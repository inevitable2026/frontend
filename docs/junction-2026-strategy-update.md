## 1. 결론

장기 전략은 유지한다.

> 회사와 현장의 변화를 먼저 감지하고, 다시 수행해야 할 안전업무와
> 필요한 문서를 준비해 주는 AI 안전 컨설턴트

다만 Junction 데모의 중심은 범용 챗봇이나 전체 안전관리 플랫폼이 아니다.
3일 동안 완결해 보여줄 핵심 업무는 하나로 좁히되, 그 업무를 가능하게 하는
공통 데이터 기반까지 실제로 만든다.

> **OCR로 현장 문서를 구조화해 회사 맥락 DB에 버전과 원문 근거를 함께
> 저장하고, 한 번 쌓인 맥락을 위험성평가 갱신과 회사 챗봇에서 재사용한다.**

이 공통 기반에서 가장 깊게 구현할 핵심 업무는 다음 하나다.

> **협력업체에서 변경 문서가 도착하면, 기존 위험성평가와 비교하여
> 영향받는 항목과 부족한 정보를 찾고, 근거가 연결된 갱신 초안을 만든다.**

회사 챗봇은 별도 제품으로 넓히지 않고, 같은 DB가 실제로 재사용된다는 것을
`왜 이 위험성평가를 다시 해야 해?`라는 한 번의 근거 질문으로 증명한다.
법령 조회, TBM, 순회점검, 월간보고는 이후 소비자(consumer)로 남긴다.

따라서 데모 메시지는 **one ingestion pipeline, two working outcomes**다.

1. 변경 맥락이 위험성평가 갱신 업무를 시작시킨다.
2. 같은 원문과 버전이 회사 챗봇의 근거 답변에도 쓰인다.

## 3. 업데이트된 제품 정의

### 한 문장

> **현장 문서를 검증 가능한 회사 맥락으로 축적하고, 그 맥락의 변화를 감지해
> 위험성평가 갱신과 근거 기반 질문 응답까지 이어 주는 Document Agent.**

### 사용자와 업무

- 주요 사용자: 원청 소속 현장 안전관리자
- 촉발 상황: 협력업체가 자재·공법·장비·일정 변경 문서를 이메일로 전송
- 사용자 업무: 변경 내용이 기존 위험성평가에 영향을 주는지 확인하고 문서를 갱신
- 현재 대안: 이메일 첨부, 계약서, 자재표, 기존 평가표를 사람이 직접 대조
- 즉시 결과: 변경된 항목, 영향 가능성이 있는 위험요인, 부족한 현장 정보,
  갱신 초안과 원문 근거

### 제품의 두 계층

```text
공통 기반
문서 수집 -> Studio OCR/분류/추출/검증 -> 회사 맥락 DB

결과 A: 변경 사실 비교 -> 위험성평가 갱신 초안 -> 사람 승인
결과 B: 회사 문서 검색 -> 정확 원문 읽기 -> 근거 기반 챗봇 답변
```

여기서 회사 맥락 DB는 단순한 벡터 DB나 문서 보관함이 아니다. 각 사실이
`어느 현장`, `어느 문서 버전`, `몇 페이지의 어떤 영역`에서 왔는지 추적할 수
있는 **감사 가능한 현장 맥락 원장(auditable site-context ledger)**이다.

위험성평가와 챗봇은 별도 데이터 복사본을 만들지 않고 이 원장의 동일한
문서 버전과 근거 블록을 읽는다. 이번 데모에서 위험성평가는 주 업무이고,
챗봇은 공통 기반의 재사용성과 설명 가능성을 보여주는 제한된 두 번째 소비자다.

구매자는 아직 검증되지 않았다. 원청 본사 안전조직 또는 중견 건설사의 현장
책임자를 초기 가설로 두되, 해커톤 피치에서 확정 사실처럼 말하지 않는다.

## 4. 핵심 가치 루프

```text
협력업체 변경 이메일/문서 수신
  -> 변경 이벤트 생성
  -> 원본 문서와 버전 우선 저장
  -> 첨부 문서 구조화·분류·검증
  -> 추출 사실과 원문 좌표를 회사 맥락 DB에 저장
  -> 이전 버전 및 기존 위험성평가와 변경 사실 비교
  -> 변경 전후 비교 및 부족 정보 확인
  -> 안전관리자에게 재검토 업무 알림
  -> 현장 사진/텍스트 보완
  -> 위험성평가 갱신 초안 생성
  -> 사람이 근거를 확인하고 승인
  -> 같은 근거를 회사 챗봇에서 정확 원문으로 다시 읽어 설명
```

가치 사건(value event)은 챗봇이 답변한 순간이 아니다.

> 안전관리자가 변경 문서의 원문 근거와 함께 갱신 초안을 검토 가능한 상태로
> 받은 순간

공통 기반의 성공 조건은 **ingest once, use twice**다. 위험성평가 초안과 챗봇
답변의 각 주장은 출처에 연결되어야 하며, 두 결과에서 공유하는 설명 주장은
같은 `document_version/source_block`을 재사용해야 한다. 두 결과의 전체 근거
집합이 완전히 같을 필요는 없다. 챗봇은 특히 변경 통지와 기존 위험성평가의
두 필수 근거를 모두 포함한다.

## 5. Upstage Studio와 회사 맥락 아키텍처

동일한 수집 파이프라인으로 다음 세 문서 유형만 처리한다.

- 협력업체 변경 안내 이메일 또는 변경 공문
- 신규 자재표/사양서
- 기존 위험성평가 PDF

Studio Agent 구성:

```text
이메일/업로드
  -> 원본 파일 및 수신 메타데이터 저장
  -> Parse
     이메일·스캔 PDF·표·체크박스·도장을 구조화하고 좌표 보존
  -> Classify
     변경통지 / 자재사양서 / 기존 위험성평가로 분류 및 분리
  -> Extract
     문서 유형별 schema로 핵심 필드 추출
  -> Validate
     필수 필드·신뢰도·원문 근거 확인
  -> 회사 맥락 DB
     문서·버전·사실·원문 블록·변경 관계를 영속 저장
     |-> 위험성평가 비교 -> Instruct -> 영향 후보·부족 정보·갱신 초안
     `-> 회사 챗봇 -> 후보 검색 -> 정확 원문 읽기 -> 근거 답변
```

권장 추출 schema:

| 문서 유형 | 추출 필드 |
| --- | --- |
| 변경 통지 | 현장, 발신사, 변경 사유, 적용일, 영향 공종, 담당자 |
| 자재 사양 | 품목, 제조사, 모델, 규격/재질, 수량, 사용 위치, 이전 값, 변경 값 |
| 기존 위험성평가 | 작업 단계, 위험요인, 현재 대책, 담당자, 평가일, 관련 근거 |

### 최소 회사 맥락 데이터 모델

| 엔터티 | 데모에 필요한 최소 필드 |
| --- | --- |
| 문서 | 회사, 현장, 문서 유형, 논리 문서 키, 제목 |
| 문서 버전 | 버전, 원본 위치, checksum, 적용일, 수신일, 이전 버전, Studio run, 처리 상태 |
| 원문 블록 | 문서 버전, 페이지, 순서, 텍스트, bounding box, 페이지 크기, 좌표계 |
| 추출 사실 | schema key, 값, 정규화 값, confidence, 검증 상태, 원문 블록 |
| 변경 관계 | 이전 사실/버전, 새 사실/버전, 변경 유형, 영향 후보 |
| 현장 관찰값 | 회사, 현장, 작성자, 작성 시각, 입력 종류, 값, 검증 상태, 선택적 첨부 문서 버전·블록 |
| 업무 산출물 | 위험성평가 초안, claim 단위 내용, 상태, 승인자·승인일, 연결된 문서 또는 관찰 근거 ID |

핵심 저장 규칙:

- 원본과 OCR 결과는 덮어쓰지 않고 버전별로 보존한다.
- 추출값은 confidence와 `validated / needs_review` 상태를 함께 저장한다.
- 사진·텍스트 보완은 출처 없는 문자열로 합치지 않고 작성자·시각·검증 상태가
  있는 현장 관찰값으로 저장한다. 첨부 파일은 가능하면 문서 버전·원문 블록에 연결한다.
- 초안과 답변의 각 주장은 불변 문서 버전·원문 블록·checksum 또는 현장 관찰값에 연결한다.
- bounding box와 함께 페이지 크기와 좌표계를 저장해 원문 하이라이트가 어긋나지 않게 한다.
- 데모에서는 세 문서 schema의 필드·본문 검색으로 제한한다. 범용 ontology나 고도화된 vector search는 P0가 아니다.

### 회사 문서 조회 도구 계약

| 도구 | 역할 | 인용 가능 여부 |
| --- | --- | --- |
| `search_company_documents` | 허용된 현장 안에서 관련 문서·버전 후보를 찾고 임시 ref 반환 | 불가 - 후보 선택용 |
| `read_company_document` | ref가 가리키는 정확한 문서 버전과 페이지·원문 블록을 읽음 | 가능 - 답변 근거용 |

챗봇은 검색 결과 요약만 보고 답하지 않는다. 먼저 후보를 고른 뒤 정확한 원문을
읽고, 필요한 양쪽 자료를 모두 읽은 경우에만 답한다. 예를 들어 `왜 재평가가
필요해?`에는 신규 변경 통지와 기존 위험성평가를 각각 읽어야 한다.

회사·현장 범위는 모델의 도구 인자가 아니라 서버가 주입하는 신뢰 컨텍스트에서
강제한다. 3일 데모는 실제 로그인 시스템 대신 단일 회사·단일 현장·고정 데모
사용자 범위를 서버 설정으로 주입할 수 있다. 모델은 회사·현장 ID를 지정하거나
바꿀 수 없다. search와 read 모두 이 범위를 적용하며, search의 ref는 세션 또는
요청 안에서만 유효한 불투명 매핑이다. read는 범위를 다시 검사하고 알 수 없거나
다른 범위의 ref를 거부한다. 데이터에는 회사/현장 식별자를 저장하되, 실제 사용자
인증이나 다중 조직 IAM·역할별 권한 UI를 완성했다고 주장하지 않는다.

Studio 밖의 역할:

- 메일 MCP/webhook: 새 문서가 도착했다는 trigger와 첨부 수집
- Next.js 앱: 업무 인박스, 보완 입력, 원문 좌표 표시, 승인 UI
- 회사 맥락 DB: 원본·버전·추출 사실·근거·업무 산출물의 영속 저장
- 공식 법령 도구: 필요한 경우 법령 후보 검색과 정확 원문 확인
- 앱 로직: 사용자 승인 전 상태 관리, 감사 이력, 결과 export

중요한 메시지:

> 외부 연동이 트리거를 만들고, Upstage Studio가 문서를 이해·구조화·검증하며,
> 회사 맥락 DB가 그 결과를 근거와 함께 기억한다. 앱은 같은 기억을 사용해
> 위험성평가 업무를 끝내고 질문에도 답한다.

## 6. 데모 시나리오

### 골든 시나리오

협력업체 이메일:

> 가격 및 납기 문제로 외장 패널 단열재를 A 제품에서 B 제품으로
> 변경하며, 다음 주 시공분부터 적용합니다.

기존 위험성평가에는 A 제품 기준의 작업방법과 위험요인이 기재되어 있다.

### 90초 데모 흐름

1. 기존 위험성평가 PDF를 OCR하고 회사 맥락 DB에 저장한다.
   - 문서 버전, 평가 행, 원문 페이지·영역이 연결된다.
2. 신규 변경 통지와 자재 사양서를 OCR하고 같은 현장에 저장한다.
   - 원본, 추출 사실, 적용일, 이전 문서와의 변경 관계가 남는다.
3. 앱이 이전·현재 사실을 비교해 홈에 `새로운 안전업무` 카드를 만든다.
   - `자재 사양 변경이 감지됐어요.`
   - 출처: 협력업체 이메일과 첨부 자재표
4. 카드를 열면 Studio 처리 단계가 보인다.
   - Parse 완료
   - Classify: 변경 통지 / 자재표 / 기존 위험성평가
   - Extract: 변경 전후 필드
   - Validate: 원문 좌표와 누락 필드
5. 문서 뷰어에서 추출한 값과 원문 영역을 함께 강조하고, 기존 평가표에서
   영향 가능성이 있는 행을 보여준다.
6. 확정에 필요한 정보가 없으면 사진 또는 텍스트를 요청한다.
   - 실제 설치 위치
   - 작업 방식 변경 여부
   - 중량·가공·취급 방식 차이
7. 사용자가 정보를 보완하면 변경된 행만 포함한 위험성평가 갱신 초안과
   변경 이력이 생성된다.
8. 안전관리자가 원문 근거를 확인하고 승인 또는 반려한다.
9. 마지막으로 회사 챗봇에 `왜 이 위험성평가를 다시 해야 해?`라고 묻는다.
   - `search_company_documents`로 후보를 찾는다.
   - `read_company_document`로 신규 변경 통지와 기존 평가표의 정확한 버전·원문을 읽는다.
   - 답변에서 양쪽 페이지를 열고, 초안과 동일한 근거 블록이 강조된다.

마지막 챗봇 장면은 자유 질의 데모가 아니라 10-15초짜리 재사용 증명이다.
핵심 업무의 흐름을 끊지 않으면서 **한 번 수집한 근거가 두 결과를 실제로
움직인다**는 점만 보여준다.

### 데모 실패 복구

- 이메일 연동 실패: 동일 샘플 이메일을 수동 업로드하는 fallback 제공
- Studio 호출 실패: 먼저 저장한 원본과 처리 상태로 재시도하고 중복 버전을 만들지 않음
- Extract 누락: 누락 필드를 표시하고 사용자가 직접 보완
- 낮은 신뢰도 추출: `needs_review`로 저장하고 확정 사실이나 답변 근거로 사용하지 않음
- 영향 판단 불확실: 자동 확정하지 않고 `추가 확인 필요`로 분류
- 챗봇 exact-read 실패: 검색 후보만으로 답하지 않고 원문 확인 실패를 표시
- 법령 조회 실패: 법적 의무를 생성하지 않고 공식 원문 확인 필요 상태 표시
- 생성 실패: 추출된 변경 전후 표까지는 보존하고 다시 생성 가능

## 7. 정보 구조 업데이트

권장 메뉴 순서:

1. 오늘의 안전업무
2. 위험성평가
3. TBM·순회점검
4. 현장 맥락 관리
5. 우리 회사 챗봇

`Daily / Schedule / Trigger`는 별도 메뉴가 아니라 홈 인박스의 필터 또는
업무 카드 배지로 사용한다.

- Daily: 매일 반복되는 작업
- Schedule: 특정 일자에 예정된 작업
- Trigger: 문서·메일·현장 조건 변화로 발생한 작업

해커톤 데모는 Trigger 카드 하나만 실제 end-to-end로 동작시킨다. Daily와
Schedule은 화면 예시 또는 더미 데이터로만 보여줄 수 있지만, 작동한다고
주장하지 않는다.

## 8. 3일 MVP 범위

### 현재 구현과의 간극

현재 저장소에는 다음이 이미 있다.

- Next.js 관리자 콘솔과 반응형 UI
- Solar Chat Completions 기반 tool loop
- 공식 법령 후보 검색과 원문 조회
- 사용자에게 보이는 tool call과 공식 출처

하지만 다음은 아직 없다.

- Upstage Studio Agent 호출
- Parse/Classify/Extract/Validate/Instruct 기반 문서 처리
- 실제 문서 업로드와 처리 상태
- 원본 문서·OCR 결과·추출 사실을 보존하는 회사 맥락 DB
- 문서 버전과 변경/supersession 관계
- 원문 좌표 기반 추출값 표시
- 변경 문서와 기존 위험성평가의 구조화 비교
- 갱신 초안 승인/반려 상태
- 회사 문서 후보 검색과 정확 원문 읽기 도구

따라서 다음 개발 우선순위는 법령 챗봇 기능 확장이 아니라 **Studio 문서 수집
파이프라인과 최소 회사 맥락 DB의 end-to-end 연결**이다. 현재 챗봇 UI와
tool loop는 보존하고, 회사 문서용 search/read 도구를 연결해 공통 데이터의
두 번째 소비자로 사용한다.

### P0 - 반드시 실제로 동작

- 변경 이메일 또는 문서 업로드
- Upstage Studio Parse, Classify, Extract, Validate, Instruct 실행
- 기존 위험성평가 PDF 입력
- 원본 파일과 처리 상태의 실제 영속 저장
- 단일 현장의 최소 회사 맥락 DB
- 문서·버전·적용일·이전 버전 관계 저장
- OCR 원문 블록, 페이지·bounding box, 추출 사실, confidence·검증 상태 저장
- 변경 전후 구조화 결과와 원문 좌표 표시
- 영향 가능성이 있는 위험성평가 행 표시
- 부족 정보 1-3개 요청 및 사용자 보완
- 보완 사진·텍스트를 작성자·시각·검증 상태가 있는 현장 관찰값으로 저장
- 각 주장에 문서 버전·원문 블록 또는 현장 관찰값이 연결된 갱신 초안 생성
- 승인/반려 및 변경 이력
- `search_company_documents -> read_company_document` 도구 연결
- 서버가 고정 데모 회사·현장 범위를 주입하고 search/read 양쪽에서 강제
- 불투명한 요청/세션 단위 ref와 read 시 scope 재검사·unknown/cross-scope 거부
- 세 데모 문서를 근거로 한 챗봇 질문 `왜 이 위험성평가를 다시 해야 해?` 1건
- 새로고침 후 저장된 문서·처리 결과·초안 복구
- 실패/재시도 상태

### P1 - 시간이 남으면

- 메일 MCP 자동 trigger
- 공식 법령 원문 조회를 갱신 화면에 연결
- 결과 PDF 또는 XLSX export
- TBM 기록 1개 연결

### 이번 데모에서 제외

- 모든 건설 법령의 완전 자동 판정
- 전체 TBM/순회점검/아차사고 워크플로
- 범용 회사 위키 UI와 전사 문서 이관
- 임의 문서 형식과 모든 회사 문서에 대한 범용 질의
- 고도화된 vector search와 범용 회사 ontology
- 자재 가격 최적화와 전략 컨설팅
- 감리·발주처까지 포함한 다중 조직 IAM과 역할별 권한 UI
- 자동 승인, 자동 제출, 작업 중지 제어

단, 위 제외 범위는 저장 기반을 빼겠다는 뜻이 아니다. 이번 시나리오의 세 문서를
실제로 저장·버전관리하고 원문 근거를 조회하는 최소 회사 맥락 DB는 P0다.

## 9. 피치 구성

### Slide 1 - 한 장면

> 어제 협력업체가 자재 변경 문서를 보냈습니다.
> 현장은 내일 바뀌지만 위험성평가표는 여전히 이전 자재 기준입니다.

제품 설명보다 변경 이메일과 오래된 평가표의 불일치를 먼저 보여준다.

### Slide 2 - 문제

> 안전관리자에게 부족한 것은 문서가 아니라, 어떤 변화 때문에 어떤 문서를
> 다시 검토해야 하는지 알려주는 연결입니다.

메일, 자재표, 계약서, 평가표가 흩어져 있고 안전관리자가 직접 비교한다.

### Slide 3 - 솔루션

> **한 번 읽은 현장 문서가, 위험성평가 갱신과 근거 기반 질문 응답을
> 동시에 움직입니다.**

`수집/OCR -> 회사 맥락 DB -> 위험성평가 갱신 + 근거 답변` 구조를 먼저
보여주고, 주 업무 흐름은 `감지 -> 비교 -> 보완 -> 초안 -> 승인`으로 좁힌다.

### Slide 4 - Live demo

설명보다 실제 end-to-end 실행에 시간을 사용한다. 처리 노드는 별도 개발자
로그가 아니라 사용자 화면 안에서 신뢰 증거로 보여준다.

### Slide 5 - Why Upstage Studio

- Parse: 복잡한 평가표와 자재표의 표/레이아웃/좌표 보존
- Classify: 번들 문서를 유형별 분기
- Extract: 문서별 schema로 변경값과 평가 행 추출
- Validate: 누락 또는 낮은 신뢰 결과를 사람에게 돌려보냄
- Instruct: 원문 근거 기반 영향 요약과 갱신 초안
- REST/webhook: 메일과 관리자 콘솔 연결
- Context store: Studio가 읽은 사실과 원문 좌표를 버전별로 보존해 두 결과에서 재사용

### Slide 6 - 차별점

| 기존 방식 | 우리 제품 |
| --- | --- |
| 문서를 업로드한 뒤 질문 | 문서 변화가 먼저 업무를 생성 |
| 문서 요약/OCR에서 종료 | 갱신 가능한 안전 문서 초안까지 생성 |
| 결과만 제공 | 원문 좌표, 변경 전후, 승인 이력 제공 |
| 일반 RAG는 관련 문서를 찾아 답변 | 변경 사실을 버전·좌표와 함께 저장하고 안전업무를 만든 뒤 같은 근거로 답변 |

### Slide 7 - 확장 비전

> 회사 맥락 DB는 기능 목록이 아니라 재사용 가능한 안전 의사결정의 기반입니다.
> 오늘은 변경관리 한 건과 `왜?`라는 근거 질문 한 건으로 이를 증명합니다.

같은 현장 맥락과 승인 이력은 이후 TBM, 순회점검, 감사 대응으로 확장한다.

자재 최적화나 전체 건설 AX는 마지막 한 문장으로만 남긴다.

## 10. 심사 기준별 방어 전략

### Upstage Technology Implementation - 30

- Studio 화면 또는 agent diagram을 직접 보여준다.
- 각 노드의 입력과 출력을 우리 앱의 단계와 연결한다.
- 단순 Solar API 호출만으로 Upstage 활용을 설명하지 않는다.
- Extract 값에서 원문 좌표로 이동하는 상호작용을 보여준다.
- 최소 1개의 낮은 신뢰도/누락값 보완 경로를 보여준다.

### Idea Creativity - 25

- `건설 문서 OCR`로 소개하지 않는다.
- `OCR + vector DB + 챗봇`으로도 소개하지 않는다.
- `문서 변화가 다음 안전업무를 먼저 시작시키는 에이전트`로 소개한다.
- 기존 서비스와의 차이는 모델보다 버전·원문 좌표가 유지되는 회사 맥락,
  trigger, closed-loop workflow에 둔다.

### Product Planning - 25

- 사용자: 원청 현장 안전관리자
- 문서: 변경 공문, 자재 사양서, 기존 위험성평가
- 업무: 변경 영향 확인과 갱신 초안
- 범위: 단일 trigger 시나리오
- 완료 정의: 사람이 근거를 확인하고 승인 가능한 초안
- 기반 증명: 두 결과의 공유 주장이 같은 불변 원문 근거를 재사용하며,
  챗봇이 변경 통지와 기존 위험성평가의 두 필수 근거를 모두 읽음

### Service Completeness - 20

- 데모 데이터와 순서를 고정한다.
- 외부 메일 장애를 위한 수동 업로드 fallback을 둔다.
- 로딩, 부분 실패, 누락 필드, 재시도, 승인 상태를 구현한다.
- 새로고침 후에도 데모 결과를 복구할 수 있게 샘플 세션을 준비한다.
- 각 출력 claim에 문서 또는 현장 관찰 provenance가 있고, 두 결과의 공유 claim이
  같은 불변 원문 ref를 재사용하며, 챗봇이 변경 통지와 기존 위험성평가의 두 필수
  근거를 모두 포함하는지 데모 전 자동 확인한다.

## 11. 증거와 가정

### Verified

- 공식 트랙은 Upstage Studio 기반 Document Agent와 실제 문서 업무 완료를 요구함.
- 평가에서 Studio 구현이 가장 높은 단일 배점인 30점임.
- 제품 계획은 3일 제약에 맞춘 구체적인 사용자·문제·화면·데이터 흐름을 평가함.
- Studio는 Parse, Classify, Extract, Validate, Instruct와 REST/webhook 연동을
  제품 기능으로 제시함.

### Reported

- 팀 논의에서는 위험성평가가 현장 변화에 맞춰 반복 검토되어야 하고,
  안전관리자가 여러 이해관계자의 정보를 따라가기 어렵다는 문제를 제기함.
- 팀은 메일 MCP, brownfield 문서 OCR, 데스크 앱, 메인 시나리오를 병렬로
  구현하는 역할 분담을 논의함.
- 제품 책임자는 OCR로 회사 DB를 만들고, 축적된 내용을 위험성평가 생성과
  챗봇 양쪽에서 재사용해야 한다고 범위를 명확히 함.

### Assumed

- 자재 또는 공법 변경 문서가 안전관리자가 실제로 자주 놓치는 trigger 중 하나임.
- 위험성평가 변경 초안이 문서 요약보다 더 강한 사용자 가치를 제공함.
- 해커톤 샘플 문서로 Studio 추출 schema를 안정적으로 시연할 수 있음.
- 동일한 근거의 재사용을 보여주는 제한된 챗봇 질문이 피치를 분산시키지 않고
  회사 맥락 기반의 확장성을 증명할 수 있음.

### Unknown

- 어떤 변경 문서가 실제 현장에서 가장 빈번하고 비용이 큰지
- 기존 위험성평가 양식의 현장별 편차
- 안전관리자가 허용할 자동화 범위와 필수 승인 절차
- 구매자와 예산 소유자
- 실제 문서 기준 추출 정확도와 처리 시간
- Studio 출력의 page/bounding-box 형식과 앱 문서 뷰어 좌표계의 실제 호환성

### 핵심 제품 리스크

1. **오추출 전파**: 잘못 읽은 사실이 회사 맥락 DB에 확정값으로 들어가면
   위험성평가와 챗봇이 동시에 틀린다. 낮은 신뢰 결과는 `needs_review`로
   격리하고 사람이 확인하기 전에는 확정 사실로 쓰지 않는다.
2. **근거 드리프트**: 최신 문서만 가리키면 이후 업로드 뒤 과거 초안과 답변의
   근거가 바뀐다. 모든 산출물을 불변 문서 버전·원문 블록·checksum에 고정한다.
3. **두 제품처럼 보이는 문제**: 챗봇 자유 질의나 위키 탐색을 길게 보여주면
   핵심 변경관리 흐름이 흐려진다. 챗봇은 한 번의 `왜?` 질문으로만 재사용을 증명한다.
4. **권한 완성 착시**: 회사·현장 컬럼만으로 enterprise 권한이 완성되지는 않는다.
   단일 데모 사용자와 서버 측 현장 필터까지만 구현하고 그 이상은 주장하지 않는다.

## 12. 즉시 검증할 다섯 가지

1. 세 샘플 문서를 Studio에 넣고 문서 유형, 추출 schema, page/bounding-box가
   회사 맥락 DB에 저장·복구되는지 오늘 확인한다.
2. 같은 샘플로 기존 평가표와 변경 사실을 비교해 갱신 초안을 만들고,
   `왜 이 위험성평가를 다시 해야 해?`에 양쪽 정확 원문을 읽어 답하는지 확인한다.
   각 claim에 provenance가 있고, 공유 claim은 같은 불변 원문 ref를 재사용하며,
   챗봇은 두 필수 문서를 모두 읽어야 통과다.
3. 오추출 또는 필수값 누락 샘플 1건을 넣어 `needs_review`가 두 소비자의 확정
   결과에서 제외되는지 확인한다.
4. 안전관리자 또는 도메인 인터뷰 대상에게 변경 이벤트 3개를 보여주고
   가장 자주 놓치는 문서를 고르게 한다.
5. 한 명이 설명 없이 데모를 수행해 업로드부터 승인 가능한 초안과 근거 질문까지
   막힘 없이 완료되는지 확인한다.

## 13. 최종 피치 문장

> 건설 현장의 안전문서는 한 번 작성하고 끝나는 문서가 아닙니다.
> 자재, 공법, 일정이 바뀌면 기존 평가가 현재 현장을 반영하는지 다시
> 확인해야 합니다. 하지만 그 변화는 이메일과 첨부 문서에 흩어져 있습니다.
>
> 우리는 Upstage Studio로 변경 문서와 기존 위험성평가를 읽고 분류하고,
> 추출한 사실을 문서 버전과 원문 좌표가 보존된 회사 맥락 DB에 쌓습니다.
> 새로운 변경이 들어오면 안전관리자에게 먼저 재검토 업무를 만들고,
> 부족한 현장 정보를 받은 뒤 근거가 연결된 갱신 초안까지 준비합니다.
>
> 한 번 읽은 문서는 여기서 끝나지 않습니다. 안전관리자가 왜 재평가가
> 필요한지 물으면, 같은 기존 평가표와 신규 변경 문서의 정확한 원문을 다시
> 읽어 답합니다. 하나의 문서 수집 파이프라인이 두 가지 실제 업무를 움직입니다.
>
> 문서를 이해하는 AI를 넘어, 변화가 생겼을 때 안전업무를 실제로 끝내는
> Document Agent입니다.
